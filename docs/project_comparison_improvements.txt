================================================================================
          DAYTONE MOOD ANALYSER - INITIAL STATE VS. IMPROVED PRODUCT
================================================================================

This document compares the early initial state of the DayTone codebase to the
fully polished, secure, and deployed production application.

--------------------------------------------------------------------------------
1. SIDE-BY-SIDE COMPARISON TABLE
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------
2. DETAILED COMPARISON OF KEY MILESTONES
--------------------------------------------------------------------------------

A. SECURITY & COMPLIANCE (GDPR/SOC-2)
- Initial: The application processed sensitive, highly personal mental health journal
  reflections, but saved them in raw, clear text in the database. Furthermore, users 
  who signed up had no control over their data—violating modern privacy laws.
- Improved:
  * Hybrid Encrypted Model Fields: By implementing a custom SQLAlchemy getter/setter
    harness utilizing Fernet cryptography, every single user log reflection is 
    encrypted before it is written to the database.
  * Audit Trail Logging: Added a database AuditLog model and custom utility to log 
    all admin activities (e.g. edits, deletes) ensuring accountability.
  * Account Purging: Integrated cascading database deletes so a user's entire footprint 
    is wiped instantly upon deleting their account.

B. ACCESSIBILITY & USER UX (WCAG 2.1 / PWA)
- Initial: Navigating with a keyboard was impossible because there were no focus-ring
  outlines. Mobile devices suffered from layout overflows, and dropping connection 
  rendered the site completely useless.
- Improved:
  * Responsive Flex Grid: Refined custom CSS grids to fit all mobile and tablet layouts.
  * WCAG Landmarks: Introduced `<main>`, `<header>`, and `<footer>` tags, hidden 
    skip-links, and explicit ARIA labels on button triggers.
  * Service Worker Pre-Caching: Programmed sw.js to store app shell assets (CSS, 
    icons, common scripts) locally in the cache so pages load instantly on subsequent 
    visits and work offline.

C. SYSTEM PERFORMANCE & PAGE LOAD SPEED
- Initial: Page speed was bottlenecked because heavy dependencies like three.min.js
  and chart.umd.min.js were loaded in the global base.html header, blocking initial 
  page paint. Google Fonts were also blocking the page render.
- Improved:
  * Dynamic Dependency Injection: Moved heavy script tags out of base.html and placed 
    them inside block scripts in login.html, dashboard.html, and admin templates.
  * Font Load Deferral: Reconfigured Google Fonts using link preloading, loading 
    asynchronously to prevent blocking page renders.
  * CSS Asset Pipeline: Created a Python minifier script to compress static CSS.

D. DATABASE COMPATIBILITY & DEPLOYMENT AUTOMATION
- Initial: Code relied on SQLite-specific parameters. Running database migrations on
  production database services (PostgreSQL) caused compatibility errors due to strict 
  boolean defaults. Deployments required manual intervention.
- Improved:
  * Database-Agnostic Migrations: Patched Alembic migration classes so default parameters 
    are resolved as database-agnostic text representations (e.g., sa.text("false")).
  * Render Blueprints: Automated the entire provisioning process in render.yaml.
  * Start Command Migration: Shifted migrations to startCommand, allowing free-tier
    deploys to build and upgrade successfully.
